# FRAME

> Discover places. Capture moments.

FRAME is a community for street photographers. It presents photographs the way a
printed magazine would — large, uncluttered, one accent colour — and then does
the thing a magazine cannot: it tells you where the frame was made and how. Every
photograph carries its place, its camera and lens, its exposure, and the
photographer who stood there. Places are a first-class entity with their own
pages and a map, submitted by members and approved by moderators, and their
coordinates are always rounded by policy so that a published location never puts
somebody's doorway on a map.

The product has an unusual rule running through it, and it is worth knowing
before you read the code: **nothing in the interface may claim something
happened that did not happen.** A capability that is not configured says so. A
write that cannot be performed explains why rather than reporting success. Demo
figures are labelled as demo figures. You will see that rule enforced in
`src/lib/config.ts`, in every server action's return type, and in the two notice
components in `src/components/system/`.

## What is wired to a backend, and what is not

This is decided by configuration rather than by a build flag, and it is worth
understanding first because it determines what you will see when you start the
app.

`isDatabaseConfigured()` in `src/lib/config.ts` asks one question: are both
`NEXT_PUBLIC_SUPABASE_URL` and a Supabase publishable key present? The answer
drives everything else.

| Capability | Turned on by | With an empty environment |
| --- | --- | --- |
| Reads — photographs, places, photographers, collections, moderation queues | `NEXT_PUBLIC_SUPABASE_URL` + publishable key | A bundled in-memory dataset answers instead: 20 photographs, 15 places, 6 photographers, 5 collections. A notice under the header says so on every page. |
| Accounts and sign-in | the same two variables | `getViewer()` returns `null`. The viewer is permanently signed out, and the header shows the signed-out state. |
| Writes — appreciate, upload, submit a place, report, collections, moderation | the same two variables | Every action refuses with one sentence: *"This action needs a database and none is configured, so nothing was saved."* Nothing is faked, and nothing is queued for later. |
| Image uploads | a database **and** a storage bucket (`STORAGE_PROVIDER`, `STORAGE_BUCKET`, or for Cloudflare R2 the three `R2_*` secrets plus `NEXT_PUBLIC_IMAGE_HOST`) | Refused, with the missing variable named. |
| Reports from a signed-out visitor | `SUPABASE_SERVICE_ROLE_KEY` | Refused with an explanation. Reports from signed-in members need no extra variable. |
| Maps | `NEXT_PUBLIC_MAP_STYLE_URL` | An explicit panel saying no map style is configured. No request is made to any tile server, and there is no fallback to a public demo one. |
| Confirmation and password-reset email | the Supabase project's own auth settings | Unavailable, because sign-up is unavailable. |

Reads go through one module, `src/lib/data/repository.ts`, which dispatches to
either the demo dataset or the Supabase queries. No component imports either
implementation directly, so both paths satisfy the same interface and the UI
cannot tell which one answered. That is also why demo mode is a genuinely
reviewable state rather than a stub: filters, pagination, empty states and the
moderation queues all work against it.

Two things that *look* like capabilities but are not configured at all:

- **Image derivatives** are generated by `sharp` in your own process, once per
  upload. No third-party transformation service is involved, and none can be
  configured.
- **Rate limits** are counted in Postgres by `check_rate_limit()`. With no
  database, `src/lib/rate-limit.ts` falls back to a per-instance in-memory
  counter and logs that it has done so. That fallback is a convenience for
  development and explicitly not a security control.

### Checking the state of your own checkout

This repository is built feature by feature, so the honest answer to "is screen
X there yet?" is in `src/app` rather than in this file — and a list written here
would be out of date before you read it. Three commands tell you the truth:

```bash
# Which routes exist right now
find src/app -name 'page.tsx' -o -name 'route.ts' | sort

# Which route folders are still empty
find src/app -type d -empty | sort

# Which write paths exist right now
ls src/server/actions/
```

The route set the project is built to is fixed, and nothing links outside it:

## Stack

| | |
| --- | --- |
| Framework | Next.js 15.5, App Router, React 19 — Server Components by default |
| Language | TypeScript 6, `strict` with `noUncheckedIndexedAccess` |
| Styling | Tailwind CSS v4, with the design tokens declared in `@theme` inside `src/app/globals.css` |
| Data and auth | Supabase — Postgres, row-level security, Supabase Auth via `@supabase/ssr` |
| Validation | Zod v4, one schema module per feature under `src/lib/validation/` |
| Images | `sharp` for the four derivatives on the server, `exifr` for reading EXIF in the browser, `next/image` for delivery |
| Maps | MapLibre GL, with no default tile provider |
| UI primitives | Radix UI, `lucide-react`, `clsx` + `tailwind-merge` |

There is no state-management library, no data-fetching library, no component
framework and no CSS-in-JS. Server Components fetch, forms post to server
actions, and the few client components are small leaves.

## Directory layout

| Path | What lives there |
| --- | --- |
| `src/app/` | Routes, layouts and the global stylesheet. `globals.css` holds every design token and is the file to read before writing a class name. `api/` holds the one route handler that is an endpoint rather than a page. |
| `src/components/` | UI, grouped by subject: `ui/` for primitives, `layout/` for the shell, `system/` for notices and toasts, and one folder per feature area — `photo/`, `photo-detail/`, `location/`, `photographer/`, `map/`, `discover/`, `collections/`, `search/`, `home/`, `auth/`, `upload/`, `moderation/`. |
| `src/lib/` | Everything that is not a component: `config.ts` (capabilities and policy), `data/` (the repository and the demo dataset), `supabase/` (three clients with three privilege levels), `validation/`, `storage/`, `images/`, `auth.ts`, `rate-limit.ts`, `geo.ts`, `ranking.ts`, `seo.ts`, `utils.ts`. |
| `src/server/actions/` | Server actions, one module per feature. Each returns a structured `ActionResult`; none throws for an expected failure. |
| `src/types/` | `domain.ts`, the hand-written contract the whole UI depends on. Not generated, and not to be replaced by generated output. |
| `supabase/` | The database: numbered migrations, `seed.sql`, and the local CLI config. `supabase/README.md` is the best document in the repository — read it before writing a query. |
| `docs/` | This documentation, plus `docs/prototype/` — the static HTML the visual language and the design tokens were taken from. |
| `.claude/` | Editor tooling configuration. Not part of the application. |

At the root: `middleware.ts`, which refreshes the Supabase session and does
nothing else; `next.config.mjs`, which holds the image allow-list and the
security headers; and `tsconfig.json`, `postcss.config.mjs` and
`eslint.config.mjs`. All five are treated as fixed — see
[Conventions](#conventions-worth-knowing-before-you-change-anything).

## Run it locally

You need **Node 20.9 or newer** and npm 10. That floor comes from `sharp`, not
from Next.js: `sharp` declares `engines.node >= 20.9.0`, and it is what builds
the image derivatives. The project was developed on Node 20.19.0.

```bash
node -v   # expect v20.9.0 or newer
```

Nothing else: no Docker, no database, no credentials.

**1. Install dependencies.**

```bash
npm ci
```

Use `npm ci` rather than `npm install` so the lockfile is honoured exactly.
`sharp` is a native module and will fetch the prebuild for your platform here.

**2. Start it, with nothing configured.**

```bash
npm run dev
```

Open <http://localhost:3000>. This is the demo-mode shortcut, and it needs no
credentials, no `.env.local` and no external service of any kind. You get the
whole interface over the bundled dataset, with a notice saying exactly that and
every write path refusing honestly. It is the right way to review the UI, and
the right way to start on a Monday morning.

**3. When you want to configure something, copy the example file.**

```bash
cp .env.example .env.local
```

`.env.example` is committed and contains placeholders only; `.env.local` is
git-ignored. Every variable is commented in place, and
[`docs/ENVIRONMENT.md`](docs/ENVIRONMENT.md) explains what each one does and
what happens without it. Restart `npm run dev` after editing it — the dev server
reads the environment at startup.

One trap, called out here because it is the natural next keystroke: the two
`NEXT_PUBLIC_SUPABASE_*` lines in `.env.example` are **uncommented
placeholders**, so copying the file and starting the app without editing it
takes you out of demo mode and points every read at a project that does not
exist. Either put your own values in both, or comment both lines out and stay on
the bundled dataset. `isDatabaseConfigured()` checks that the variables are
present, not that they resolve — nothing can check that for you.

**4. Optionally, turn on the map.** This one is independent of the database, so
it is the cheapest capability to add first. Set `NEXT_PUBLIC_MAP_STYLE_URL` to a
style URL from a tile provider whose terms allow your traffic, and
`NEXT_PUBLIC_MAP_ATTRIBUTION` to the credit that provider requires.
[`docs/EXTERNAL-SERVICES.md`](docs/EXTERNAL-SERVICES.md) explains the choice, and
why the project deliberately ships no default.

## npm scripts

| Script | What it runs | Notes |
| --- | --- | --- |
| `npm run dev` | `next dev` | Development server on port 3000, with hot reload. |
| `npm run build` | `next build` | Production build. Also the most thorough type check, because it type-checks route parameters and generated types that `tsc` alone does not see. Needs outbound network access, because the layout fetches Inter and Instrument Serif through `next/font/google` at build time. |
| `npm run start` | `next start` | Serves the output of a previous `npm run build`. It does not build. |
| `npm run lint` | `eslint .` | ESLint with the flat config in `eslint.config.mjs`, where `any`, raw `<img>` and several accessibility rules are errors rather than warnings. The ESLint CLI is called directly because `next lint` is deprecated and is removed in Next 16. |
| `npm run lint:fix` | `eslint . --fix` | The same rules, applying every fix that can be applied safely. |
| `npm run typecheck` | `tsc --noEmit` | Strict, with `noUncheckedIndexedAccess`. Faster than a build for a quick check, and not a substitute for one. |

There is one more check that is not an npm script, because it needs a database
rather than Node:

```bash
supabase/tests/run.sh
```

It applies all seven migrations to a throwaway PostgreSQL cluster and asserts the
38 guarantees in `supabase/tests/constraints.sql` — one appreciation per member,
a sourced location restriction, a published photograph that carries a rights
confirmation, and the rest. It exits non-zero on failure and never touches a
database holding real data. `supabase/tests/README.md` says what a green run does
and does not prove.

**All four run in CI.** `.github/workflows/ci.yml` runs the lint, typecheck and
build in one job and the database suite in another, on every pull request and
every push to `main`. The database job uses a PostGIS service container, so the
migrations apply unmodified rather than through the local shim, and a final step
asserts that `locations.geog` really is `geography(Point,4326)` — a run that
silently fell back to the shim would otherwise look identical to one that did
not. Node 24 is used there; `engines` in `package.json` records the floor,
because Node 20 is past end of life and `@supabase/supabase-js` warns on it.

## From demo mode to a real database

In order. Each step is reversible by removing the variables you added.

**1. Get a Postgres with the right extensions.** A Supabase project, hosted or
local. The local stack needs the Supabase CLI:

```bash
npm install -g supabase        # or: brew install supabase/tap/supabase
supabase start                 # applies supabase/migrations/ then seed.sql
```

`supabase start` prints the API URL, the publishable (anon) key and the
service-role key.

**2. Put the keys in `.env.local`.**

```bash
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<the anon key it printed>
SUPABASE_SERVICE_ROLE_KEY=<the service_role key it printed>
```

The first two are what switch the app out of demo mode. The third is server-only
and bypasses row-level security entirely; exactly one code path uses it, to file
a report from a visitor with no session, so you can leave it unset and
everything else still works. It must never acquire a `NEXT_PUBLIC_` prefix.

**3. Restart the dev server.** The notice under the header disappears, and reads
now come from Postgres. The seed loads camera and lens reference data and
fifteen approved places, and no photographs, so Discover will be empty until you
upload something. An empty state is the correct answer there, not a bug.

**4. Promote yourself to moderator.** No code path grants a role above `member`,
deliberately — the `handle_new_user()` trigger always inserts `'member'`, and a
guard trigger refuses a self-promotion even for an admin. Run the statement in
[`supabase/README.md`](supabase/README.md) as `postgres`, from the Studio SQL
editor at <http://127.0.0.1:54323>.

**5. For uploads, check the bucket.** The local stack creates it from
`supabase/config.toml`. A hosted project does not — `supabase/README.md` has the
one statement that creates it and the four policies that restrict each member to
their own prefix.

Mail sent by the local stack is caught by Inbucket at
<http://127.0.0.1:54324>, so you can complete an email confirmation without
sending anything to a real address.

For a hosted project, including the order the migrations have to run in and the
auth URLs that make confirmation links work,
[`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md) takes over.

## Conventions worth knowing before you change anything

- **`src/types/domain.ts` is the contract.** It is hand-written. The repository
  layer maps the database onto it, which is precisely what lets the demo dataset
  and the live queries satisfy one interface.
- **Reads go through `src/lib/data/repository.ts`, and nothing else.** No
  component imports the demo dataset or the Supabase queries directly.
- **Every server action returns `ActionResult`.** An expected failure is a
  returned value with a code, not a thrown exception. Each action checks the
  capability, then authenticates, then authorises, then rate-limits, then
  validates, then writes.
- **Authorisation is checked on the server, every time.** Hiding a button is a
  courtesy, not a permission check. `middleware.ts` only refreshes the session;
  the real decision is made by `requireViewer()` or `requireModerator()` in the
  page or action that does the work, and underneath that by row-level security.
- **Coordinates only ever narrow.** Read a location's position through
  `publishableCoordinates()`. Nothing in a read path may widen what a moderator
  reduced, and EXIF GPS is never published without an explicit choice.
- **EXIF is a convenience, never proof.** It prefills a form. It says which
  device wrote a file, not who holds the rights to the photograph.
- **Counters are recounted, never incremented.** There is no `+ 1` in the schema,
  so a replayed request cannot bend a number permanently.
- **Design tokens come from `src/app/globals.css`.** Read it before writing a
  class name, and invent no new colours. Shadows belong on overlays; cards use
  hairline borders.
- **Some files are fixed.** `package.json`, `package-lock.json`,
  `tsconfig.json`, `next.config.mjs`, `postcss.config.mjs`, `globals.css`,
  `src/types/domain.ts`, and the modules in `src/lib/` that encode policy —
  `config.ts`, `utils.ts`, `geo.ts`, `ranking.ts`, `images/variants.ts`,
  `data/repository.ts` and the demo dataset — are reused rather than edited. If
  one genuinely blocks you, raise it rather than working around it locally.
